# CQA: оценка качества диалогов

Прототип Conversation Quality Analytics для хакатона Freedom Broker. Команда из 4 человек, 24 часа.

**Статус: рабочий прототип.** Работают импорт набора, оценка моделью или заглушкой, подсчёт баллов с N/A, карточка с доказательствами, апелляция и решение с пересчётом, редактор чек-листа с версиями. Данные хранятся в SQLite.

## Что строим

Веб-приложение оценивает работу оператора по настраиваемому чек-листу и показывает баллы, объяснения и реплики-доказательства. Вторая часть: апелляция, решение проверяющего и пересчёт итога.

Стек:

- **Сервер:** Python, FastAPI, SQLite. Он же отдаёт интерфейс, поэтому CORS не мешает.
- **Интерфейс:** HTML, CSS и JS без сборки, так проще перенести в Dynamics 365.
- **Модель:** OpenAI или Anthropic через общий интерфейс. Есть режим-заглушка без ключа, чтобы интерфейс и тесты работали бесплатно.
- **Подсчёт баллов:** обычный код, не модель. Модель только выбирает ответы по критериям.

## Запуск

Нужен Python 3.13, на нём работает CI.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
uvicorn backend.app.main:create_app --factory --reload
```

Приложение: http://127.0.0.1:8000. Документация API: http://127.0.0.1:8000/docs.

Если порт 8000 занят, добавьте `--port 8765` и откройте этот порт.

## Модель

Режим задаётся в `.env`:

| Переменная | Значение |
|---|---|
| `CQA_EVALUATOR` | `mock` — заглушка без ключа и без затрат, ответы не зависят от смысла диалога; `llm` — настоящая модель |
| `CQA_LLM_PROVIDER` | `openai` или `anthropic` |
| `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` | Ключ выбранного провайдера |
| `CQA_LLM_MODEL` | Модель, по умолчанию `gpt-6.1-sol` для OpenAI |
| `CQA_PRICE_INPUT_PER_MTOK`, `CQA_PRICE_OUTPUT_PER_MTOK` | Цена в USD за 1 млн токенов, из неё считается стоимость оценки |

Без ключа режим `llm` не запустится и на заглушку молча не перейдёт. Ключ хранится только в `.env`.

**Стоимость одной оценки.** Замер на 15 диалогах DEV (13 чатов и 2 звонка), модель `gpt-6.1-sol`, цены из `.env.example` ($2 и $10 за 1 млн входных и выходных токенов): один вызов модели на диалог, повторов не было, от $0,012 до $0,025, **в среднем около $0,02**. Звонки дороже чатов. Одна оценка занимает около 20 секунд. Стоимость с учётом всех вызовов, включая повторы, видна в каждой оценке (`usage.cost_usd`). *Цены провайдера и итоговую стоимость подтверждает AI Engineer.*

## Как получить данные

Данные приходят из API организаторов и в репозиторий не попадают: часть диалогов реальная, а ссылка подписана.

1. Скопируйте `.env.example` в `.env`.
2. Вставьте в `CQA_DATASET_URL` адрес кнопки «Открыть GET для DEV» из PDF-гайда (стр. 3).
3. Загрузите набор кнопкой в интерфейсе или через `POST /api/dialogs/import` с телом `{"group_id": "DEV"}`.

Контрольный `group_id` подставляется в ту же ссылку. Если организаторы дадут другую подпись, обновите `CQA_DATASET_URL`.

`.env`, `data/` и `*.pdf` закрыты в `.gitignore`. Не коммитьте их.

## Как пользоваться

1. **Диалоги.** Введите `group_id` и нажмите «Импортировать». «Оценить» оценивает один диалог, «Оценить группу» — весь набор в фоне с прогрессом.
2. **Карточка.** Итог, баллы секций, по каждому критерию ответ, вес после перераспределения N/A, объяснение и ссылка на реплику или проверенный участок. При N/A показана причина. Грубая ошибка отмечена отдельно и на итог не влияет.
3. **Апелляция.** В карточке у критерия нажмите «Оспорить», напишите комментарий и «Подать апелляцию».
4. **Решение.** На экране «Апелляции» проверяющий видит спорную оценку, комментарий и фрагмент диалога. «Подтвердить оценку» или «Изменить оценку» с причиной, затем «Сохранить решение». Итог пересчитывается, исходная оценка не меняется, в карточке видны обе.
5. **Чек-лист.** Экран «Чек-лист»: измените или добавьте критерий (название, описание, вес, тип ответа, N/A с условием, шкала, подсказка модели) и нажмите «Сохранить новую версию». Версия сразу становится активной. Готовые оценки остаются на своей версии; чтобы применить новую, оцените диалог ещё раз.

### Как считаются баллы

Подробно в `docs/BRIEF.md`, раздел «Порядок расчёта баллов». Коротко: «Да» даёт полный вес, «Нет» ноль, ступень шкалы пропорциональна верхней. Веса применимых критериев приводятся к 100, поэтому вес N/A расходится по остальным, а чек-лист с суммой весов не 100 тоже даёт максимум 100. Итог округляется один раз до двух знаков, половина вверх. Код: `backend/app/scoring/engine.py`.

## Тесты

```powershell
pytest
ruff check .
```

Обычные тесты идут на синтетике и работают в CI. Правила подсчёта с 13 контрольными примерами проверяет `pytest backend/tests/scoring`.

Сравнение модели с ручным эталоном описано в `eval/README.md`. Эталон и результаты лежат только локально в `data/gold/`.

Тесты на 65 диалогах DEV (`backend/tests/api/test_dev_dataset.py`) читают локальный `data/dev.json`, скачанный из API организаторов, и сами в API не ходят. Без этого файла, в том числе в CI, они пропускаются. Как получить файл:

```powershell
curl.exe "<ссылка GET для DEV из гайда>" --create-dirs -o data/dev.json
```

## Правила работы

**Чтобы код не ломался:**

1. В `main` попадает только PR с зелёным CI и одним одобрением.
2. Один PR — одна задача: 3–4 небольших на человека вместо одного огромного в конце.
3. PR стартует черновиком с тестами-спецификацией: сначала красные, к готовности зелёные.
4. CI проверяет, что PR меняет только файлы своей роли. Роль определяется по префиксу ветки.
5. Перед слиянием ветка обновляется от `main`.

**Чтобы нейронка не путалась:**

1. В корне лежит `AGENTS.md` с описанием проекта, таблицей ролей и запретами. `CLAUDE.md` ссылается на него.
2. Первым делом нейронка смотрит ветку, определяет роль и читает свою задачу.
3. Правит только свою зону. Если нужна чужая правка, пишет об этом в PR, а не делает сама.
4. Запреты для всех: не зашивать критерии в код, оценивать только оператора, не менять исходную оценку, не коммитить секреты и данные.
